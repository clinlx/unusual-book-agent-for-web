# 从描述构建世界

## 适用场景

当用户只提供世界观概念、题材方向、主角设定、剧情梗概、爽点需求、玩法偏好、若干关键词，或者提出“帮我从这个想法搭一个世界/模组/跑团框架”时，使用本 reference。

这个流程的目标不是简单把用户的话整理成设定集，而是把用户真正想要的乐趣、冲突、欲望结构和可游玩内容，转换为可运行的游戏世界文件。

数据结构遵循 [世界数据交付约定](./WorldDataContract.md)。

## 开局类型：需先决策

无论哪种开局都**必须产出 `模组.md`**（大纲、章节索引、补充规则索引、判断节点、特殊机制、数据面板）。开局类型只决定**是否额外加 `故事.txt` + 预填主角**（见 SKILL.md"开局类型决策"）：
- **要玩家扮演一个既定主角** → 固定开局：`模组.md` 之外再加 `故事.txt`，预填主角档案，另存 `开场剧情.txt`。
- **要玩家自建角色** → 车卡开局：只产出 `模组.md`，不加 `故事.txt`，唯一 Player 使用 §D2 完整 JSON 模板，待填字段留空。
- **描述里看不出来** → 直接问用户："想扮演一个既定主角，还是自己创建角色开局？"再据此决定加不加 `故事.txt`。别默认，选错会让运行时走错开局流程。

## 核心原则

执行顺序必须是：先把握核心爽点、完善需求、然后编写故事、然后编写支线、然后编写细节，最后填入。

用户给出的描述通常只是表层材料，真正要保护的是能激发用户兴趣的特殊类型的情节。即使是某种很奇怪的癖好也要理解，因为这可能是故事不可修改的核心。

想要写好一个作品，必须深入思考和理解此类小说的核心乐趣。将这类主题提炼出来成为方法论，将乐趣内化为自己的能力和目标，举一反三，并且反复重复触发，以不同的方式触发。从而提升读者的乐趣。

如果需求存在不明确的地方，可以询问用户；如果已经能合理推断，就先写出构建计划，再根据计划修改当前世界的文件。

每当你修改任何一个已存在的文件前，确保你已经阅读过此文件。

## 理解用户需求

首先判断用户真正要的不是“设定”，而是哪一种体验。不要只停留在题材标签，例如修仙、末世、赛博、贵族、学院、克苏鲁、恋爱、经营、权谋；必须继续追问或推断这些题材里最让用户兴奋的部分。

重点识别以下内容：

- 核心爽点：用户希望反复体验的特殊情节、关系、身份变化、压迫感、反杀感、探索感、养成感、堕落感、拯救感、支配感、被迫选择感等。
- 不可修改的核心：即使表达很奇怪，也要先理解，不要回避、净化、替换或擅自改成普通套路。
- 主角位置：玩家是救世主、旁观者、棋子、反派、调查者、流浪者、继承者、怪物、被追杀者，还是某个系统中的变量。
- 主要矛盾：谁想要什么，谁阻止谁，世界默认会如何恶化，玩家介入会改变哪些轨迹。
- 玩家自由度：玩家可以在哪些层面乱玩，世界如何响应，而不是强行把玩家推回唯一剧情。

如果用户给的信息不足，但已有足够方向，可以先做合理假设并写入计划；只有当缺失信息会直接影响核心爽点时，才询问用户。

## 构建步骤

### 1. 提炼核心爽点方法论

> 完整方法论见 [DesireAndTextureCraft.md](./DesireAndTextureCraft.md)（欲望分类法、触发机制拆解、落文件方式）。本节是其在"从描述构建"场景的要点。

把用户给出的描述拆成"可重复触发的乐趣机制"。例如：

- 如果爽点是压抑后的爆发，就要设计长期压迫、误解、资源匮乏、关键反击窗口。
- 如果爽点是关系拉扯，就要设计好感度、秘密、误会、阵营压力、不可同时满足的诉求。
- 如果爽点是探索真相，就要设计多层信息、伪线索、视角锚点、错误推理的代价与补救。
- 如果爽点是成长变强，就要设计阶段目标、数值门槛、资源循环、敌人升级、社会地位变化。

这个方法论必须贯穿主线、支线、NPC、场景、物品和世界规则，不能只写在开头。

### 2. 完善需求并确定边界

在动手写世界文件前，整理出明确的构建计划。计划至少包括：

- 世界类型与基调。
- 玩家身份与初始处境。
- 主线终极目标与阶段性目标。
- 核心爽点如何在前期、中期、后期反复触发。
- 主要势力、主要NPC、关键场景、关键物品。
- 可能失败的方式，以及失败后如何转入新分支。

如果用户没有指定规则系统，可以使用当前世界结构中的通用规则；如果用户指定了特殊力量体系、属性名、修为、灵力、污染、SAN、声望等，应当保留并写入世界规则。

### 3. 编写主线故事

主线不是固定剧本，而是世界默认轨迹与玩家干预点的组合。编写主线时必须包含：

- 世界在玩家不介入时会怎样发展。
- 每个阶段的最低燃点：玩家一进入就能感到冲突已经接近爆发。
- 每个阶段的目标、阻碍、代价、失败分支。
- 关键线索至少有两个获取路径。
- 阶段结果会改变NPC态度、场景状态、世界共识或后续难度。

主线文件应当让主持人知道“现在世界正在发生什么”，而不是只知道“玩家应该去哪”。

### 4. 编写支线与可替代路径

支线不是无关填充，而是用于强化核心爽点、提供信息佐证、展示世界质感、给玩家提供绕路方案。每条支线应当至少承担一种功能：

- 揭示主线真相的一部分。
- 提供资源、盟友、敌人、道具或声望变化。
- 展示世界规则的残酷或诱惑。
- 让玩家用不同方式解决主线问题。
- 为失败后的回归主线提供机会。

支线可以被跳过，但跳过应当有后果，例如信息不足、盟友缺失、敌对势力提前行动、最终结局条件变化。

### 5. 编写细节并填入文件

细节必须服务可主持性。每个重要NPC、场景、物品、事件都要尽量落到当前世界目录结构中，而不是停留在散文设定。

从描述构建没有源文本，检定与分支全部由你设计——但标准不降：关键剧情节点要配属性/技能检定与 DC；场景要有自动触发的感知/环境检定（写明触发时机、无需玩家宣言）；每个分支判断按 SKILL.md"检定与分支触发器"七字段落成触发器，登记进 `世界状态和世界规则/检定与触发器索引.md` 并逐条落位，不得只存在于剧情散文。开场双文本（`开场白.md`、`样例开场.md`）按 SKILL.md"开场双文本"产出并精雕；样例开场只对确实待填的字段留白，处境、"你"是谁、"你"的身体与动作三样任何开局都要立住，世界观靠处境带出，不专门写一段设定交代。

需要写入或更新的内容通常包括：

- `剧情线与进度/主线剧情.md`：主线目标、阶段、默认轨迹、分支后果。
- `剧情线与进度/<Story_Index>/剧情.md`：具体剧情阶段、冲突、选择、结果。
- `剧情线与进度/<Story_Index>/目标.json`：最终目标、阶段性目标、成功和失败条件。
- `世界状态和世界规则/世界规则.md`：题材规则、属性、力量体系、社会规则。
- `世界状态和世界规则/掷骰规则.md`：DC 表、判定公式、自动检定的触发时机。
- `世界状态和世界规则/检定与触发器索引.md`：自设计检定与分支触发器的对账清单，逐条标注写入位置。
- `开场白.md` 与 `样例开场.md`：两份精雕开场文本（见 SKILL.md"开场双文本"）。
- `世界状态和世界规则/世界共识.json`：公开信息、传闻、通缉、倒计时、世界变化。
- `存档-索引-NPC/<NPC_Index>/`：核心NPC的基础信息、关系记忆、格式化记忆、背包和日志。
- `存档-世界/<Region>/<Scene>/`：关键场景、事件台本、NPC列表、物品列表。
- `存档-索引-物品/<Item_Index>/`：关键物品、线索、资源、特殊道具。

## 写作要求

使用用户偏好的语言风格。如果用户提供了原始文风或关键词，要吸收其节奏、审美和欲望结构，不要把它改成通用模板。

所有内容都要能支持游戏主持：

- 有可见信息，也有隐藏信息。
- 有明确状态，也有变化条件。
- 有默认发展，也有玩家打断后的响应。
- 有成功奖励，也有失败代价。
- 有剧情张力，也有自由探索空间。

不要为了完整而堆设定。任何设定都应当回答：玩家如何接触它、如何利用它、如何误解它、如何改变它。

## 完成标准

完成后检查以下内容：

- 核心爽点是否被清楚提炼，并在多个层面反复触发。
- 主线是否有默认轨迹，而不是只有固定流程。
- 关键NPC是否有诉求、恐惧、秘密、关系和下一步行动。
- 关键场景是否有不同阶段、可探索内容、风险和事件触发。
- 失败是否会进入新分支，而不是直接结束。
- 关键节点是否配了检定与 DC、场景是否有自动触发检定，且全部登记进 `检定与触发器索引.md` 并落位。
- 是否产出精雕的 `开场白.md`（有多开局分支、可选规则或预设卡时含开局配置面板）与 `样例开场.md`（处境、"你"是谁、"你"的身体与动作三样是否立住，留白是否只落在确实待填的字段上）。
- 世界文件是否按当前目录结构落地。
- 修改任何已存在文件前，是否已经阅读过该文件。
- **是否已运行 `validate_game_structure.js` 验证目录结构，并修复所有报错直至验证通过。**
- **验证通过后，是否已按 SKILL.md"最终询问"阅读 `reference/FinalInquiry.md` 并逐条静默自查（此前禁止阅读该文件；条目可有理由地拒绝，不可敷衍跳过；不在对话中逐题作答）。**
