# 改进现有世界

## 适用场景

当用户要求修改、扩写、修复、补全、重构、平衡、续写、增加支线、增加NPC、增加场景、调整规则、优化结构，或者对已有世界提出任何改进需求时，使用本 reference。

本流程的目标是尊重已有世界，把用户的新需求自然合并进去，使世界更完整、更可主持、更能响应玩家，而不是推翻重写。

## 核心原则

首次对话时，如果你还不了解当前世界，则需要主动阅读和理解当前世界的文件。阅读相关文件知道了解为止。

用户提出修改需求后，先判断核心诉求：用户到底想增强什么体验、修复什么断裂、补足什么可玩性。不要只执行表层文字。

如果存在关键不明确之处，可以询问用户；如果可以从当前世界合理推断，就直接编写修改计划，并根据计划修改当前世界的文件。

每当你修改任何一个已存在的文件前，确保你已经阅读过此文件。

完成所有修改后，最后执行随附的 `scripts/validate_game_structure.js` 验证目标世界目录（调用方式见 SKILL.md），并修正所有错误。

验证出错通常只是要求某些必填字段，并不代表独有字段非法。允许自行新增不存在的字段，因此很多地方都不用删除，而是整理合并（独有的字段保留），按照模组要求填写即可，例如灵力、修为等。

## 世界理解流程

在任何修改前，先建立当前世界的内部地图。不要只读用户点名的文件；如果修改会影响剧情、NPC、场景、规则、物品、世界共识，就继续阅读相关文件，直到能回答以下问题：

- 当前世界的核心题材、核心爽点、主线目标是什么。
- 玩家当前处于哪个阶段，已经发生了哪些关键事件。
- 世界默认轨迹是什么，哪些倒计时或势力计划正在推进。
- 主要NPC的诉求、恐惧、秘密、关系和下一步行动是什么。
- 关键场景现在的状态、危险性、可探索内容、NPC和物品是什么。
- 世界规则中有哪些自定义字段，例如灵力、修为、污染、好感度、声望、阶级、阵营、通缉等。
- `检定与触发器索引.md` 是否存在，是否覆盖了现有剧情的检定与分支；`开场白.md`、`样例开场.md` 是否存在。

如果现有文件中存在独有字段、特殊结构或用户自定义写法，优先保留。不要为了套模板删除它们。

## 理解修改需求

用户的表层需求可能只是“加一个NPC”或“改一下剧情”，但真正目的通常是增强某种体验。修改前要先判断：

- 用户想增强哪种核心爽点。
- 用户不满意当前世界的哪一部分：节奏、自由度、逻辑、冲突、人物、数值、文风、结构、可玩性。
- 修改会影响哪些已有文件和状态。
- 是否需要保留旧内容作为历史、传闻、误解、废案、伏笔或分支。
- 新内容如何让世界更动态，而不是增加静态设定。

只有当用户需求存在关键歧义，且无法通过当前世界合理推断时，才询问用户。否则应当基于已有世界做出最合理的判断并继续。

## 修改计划

修改计划应当写清楚实际会动哪些部分，而不是泛泛说明。计划至少包括：

- 需要阅读的文件范围。
- 需要新增、更新或整理的世界元素。
- 受影响的剧情线、NPC、场景、物品、规则和世界共识。
- 新旧内容如何合并，哪些字段必须保留。
- 修改完成后的验证方式。

如果修改会影响多个系统，按依赖顺序执行：先规则和主线，再NPC与场景，再物品与日志，最后进度与世界共识。

角色数值整理遵循 [世界数据交付约定 §D3](./WorldDataContract.md)：保留独有字段，核对并合并重复的当前数值，不新增同义副本。

## 修改方式

### 1. 整理而不是覆盖

已有内容优先整理合并。即使验证提示字段缺失，也不要粗暴删除不认识的字段。独有字段可能是世界特色，应该保留并补齐必填字段。

例如角色文件已有灵力、修为、功法、道心、污染值等字段时，应当在保留这些字段的基础上补齐姓名、性别、外貌、状态、buff栏等结构要求。

### 2. 让修改产生连锁反应

重要修改不能只落在一个文件。新增NPC可能需要：

- 写入NPC索引。
- 写入所在场景NPC列表。
- 更新与其他NPC的关系记忆。
- 更新剧情线中的出场方式。
- 更新世界共识中的传闻或公开身份。
- 必要时增加物品、任务或日志。

新增规则可能需要：

- 写入世界规则。
- 更新相关角色属性。
- 更新判定方式或资源消耗。
- 更新剧情目标中的成功、失败条件。

新增剧情可能需要：

- 写入剧情文件。
- 写入目标与进度。
- 更新相关NPC的格式化记忆。
- 更新场景台本、物品、线索和世界共识。

### 3. 保持动态主持能力

修改后的世界应当能响应玩家行动。每个重要事件尽量写清楚：

- 触发条件。
- 默认发展。
- 玩家介入方式。
- 成功结果。
- 失败结果。
- NPC反应。
- 后续影响。

不要只写“会发生某事”，还要写“如果玩家提前阻止、误解、拖延、失败、背叛或绕开，会发生什么”。

### 4. 维护时间线与状态一致性

如果修改涉及过去事件，要检查日志、记忆、世界共识与剧情进度是否一致。

如果修改涉及当前状态，要检查NPC是否在正确场景，物品是否在正确位置，任务是否符合当前进度。

如果修改涉及未来计划，要检查倒计时、势力行动、场景事件和主线阶段是否互相支撑。

### 5. 补齐硬性交付物

旧版世界可能缺少 `开场白.md`、`样例开场.md` 或 `世界状态和世界规则/检定与触发器索引.md`（验证脚本会报缺失）。把它们视为本次改进的待补档项，按 SKILL.md"开场双文本"与"检定与分支触发器"补齐——补索引时要回头扫一遍现有剧情、场景台本、世界共识和规则文件，把已存在但未登记的检定与分支收进来，并顺手排查漏网点（自动感知/理智检定、环境检定、"玩家不作为"触发的分支）。

新增或修改剧情、场景、NPC 时，伴随的检定与分支判断必须同步登记进索引并落位，不允许只更新散文。

## 验证与修正

完成所有修改后，必须执行随附的 `scripts/validate_game_structure.js` 验证目标世界目录（调用方式见 SKILL.md），并修正所有错误。

验证时遵守以下规则：

- 缺字段就补字段。
- 格式错就整理格式。
- 可合并就合并。
- 独有字段保留。
- 不因为验证器不认识某个字段就删除它。
- 不把世界特色改成通用模板。

如果验证结果要求某些必填字段，而当前世界使用了额外字段，则在保留额外字段的同时补齐必填字段。模组要求是基础结构，不是内容上限。

## 完成标准

完成后检查以下内容：

- 是否已阅读所有受影响的已存在文件。
- 修改是否真正回应用户核心诉求。
- 新内容是否与旧世界逻辑兼容。
- 关键字段是否补齐，独有字段是否保留。
- 相关剧情、NPC、场景、物品、规则、日志是否同步。
- 新增/修改内容伴随的检定与分支是否已登记进 `检定与触发器索引.md` 并落位；缺失的开场双文本与索引是否已补档。
- 玩家成功、失败、乱玩时是否都有合理后果。
- 是否已执行 `scripts/validate_game_structure.js` 并修正返回问题。
- **验证通过后，是否已按 SKILL.md"最终询问"阅读 `reference/FinalInquiry.md` 并逐条静默自查（此前禁止阅读该文件；条目可有理由地拒绝，不可敷衍跳过；不在对话中逐题作答）。**
