# 从故事文本构建世界

## 适用场景

当用户提供小说、故事原文、长篇剧情文本、章节片段、网文开头、剧本草稿，或者要求“把这个故事改成跑团模组/游戏世界/可主持剧情”时，使用本 reference。

本流程的目标不是摘要故事，而是尊重原文、拆解原文、理解原文核心乐趣，再把它转换成玩家可以进入、选择、失败、改变和回收后果的跑团剧本与世界文件。

## 开局类型：固定开局

从故事文本构建的世界**默认是固定开局**——小说已有既定主角，玩家代入这个人。因此：
- **照常产出 `模组.md`**（故事大纲、章节文件索引、补充规则索引、关键判断节点、特殊机制、数据面板）——它任何开局都不能丢。
- **额外多产出** `故事.txt`（既定主角设定）与 `开场剧情.txt`（原文开头约 1000 字）。`故事.txt` 的存在就是运行时判"固定开局、跳过车卡"的标记（见 SKILL.md"开局类型决策"）。
- 照常产出开场双文本（见 SKILL.md"开场双文本"）：`开场白.md` 写代入引导并衔接朗读 `开场剧情.txt`；`样例开场.md` 以 `开场剧情.txt` 原文为主体，禁止改写原文，衔接扩写用分割线注明。
- 把主角的 Player 文件夹**预填好**（基础信息/格式化记忆等），玩家不需要车卡。
- 例外：若用户明确希望玩家在这个世界里自建角色而非扮演原主角，才改走车卡开局——不产出 `故事.txt`、唯一 Player 保留完整 JSON 模板，仅待填字段留空（见 [世界数据交付约定 §D2](./WorldDataContract.md)），`模组.md` 照常。

## 核心原则

尊重原文，但不要把原文当成不可互动的神像。原文的文字、风格、核心乐趣和关键张力要保留；线性剧情要拆成玩家可以介入、选择、失败、绕路和改变后果的跑团剧本。

允许扩写，但不允许修改和删除原文的内容，严禁脱离原文风格。扩写的目的不是替作者重写故事，而是把原文中隐含的场景、人物反应、分支后果和主持素材补足。

想要改写好一个作品，必须深入思考和理解此类小说的核心乐趣。将这类主题提炼出来成为方法论，将乐趣内化为自己的能力和目标，举一反三，并且反复重复触发，以不同的方式触发。从而提升读者的乐趣。

玩家是可以失败的，但是失败不是结束。失败会走向另一个分支，依然可能以下一次巧妙的遭遇来回到主线；只有在错误的方向一意孤行，才走向真正不可挽回的失败。

## 原文处理流程

### 1. 保留开场

从故事原文开头摘取约1000字，写入 `开场剧情.txt`。这段内容用于主持人开局朗读或作为玩家进入世界的第一印象。

保留时注意：

- 不擅自改写原文。
- 不提前剧透后文。
- 如果原文开头不足1000字，则保留全部开头内容。
- 如果原文开头包含强烈风格、节奏、癖好、压迫感或核心冲突，要完整保留其味道。

### 2. 拆分故事集

不使用代码脚本，纯手动将原文拆成多个细章节。拆分标准不是机械字数，而是剧情功能：一次场景变化、一次关系变化、一次冲突升级、一次秘密揭露、一次选择机会，都可以成为一个独立章节。

每个章节写入 `故事集/xxx.md`。每个文件应当包含：

- 一段原文。
- 必要的扩写内容。
- 额外内容以分割线的方式注释在段落间。

允许扩写，但扩写必须贴合原文语气、节奏、审美、人物行为逻辑和题材爽点。禁止删改原文内容，禁止把原文改成另一种价值观或另一种文风。

### 3. 提炼核心乐趣

> 完整方法论见 [DesireAndTextureCraft.md](./DesireAndTextureCraft.md)（欲望分类法、触发机制拆解、落文件方式）。本节是其在"从故事构建"场景的要点。

在改写前，先总结这类小说为什么好看。不要只总结剧情发生了什么，而要总结读者为什么会继续读。

需要提炼：

- 最核心的情绪循环：期待、压迫、暧昧、恐惧、反杀、羞辱、成长、失控、救赎、堕落、复仇、占有、探索等。
- 最重要的人物关系：主从、师徒、宿敌、共犯、救赎者与被救者、利用与反利用、误解与真相等。
- 最有张力的场景类型：审判、逃亡、夜谈、禁地、仪式、公开羞辱、秘密交易、绝境选择等。
- 反复触发爽点的方法论：每卷、每章、每个重要NPC和每个关键场景都要用不同方式再次触发。

这些方法论要进入后续模组设计，而不是只作为读后感。

## 跑团改写流程

### 1. 把线性故事变成可选择事件

原文里的剧情通常是固定发生的。改成跑团剧本时，要拆成：

- 不可删除的核心张力。
- 可替换的展示方式。
- 玩家可介入的时机。
- 玩家失败后的分支。
- NPC根据玩家行为产生的反应。

例如原文中“主角被迫参加审判”，跑团中可以保留“审判带来的公开压迫与身份危机”这个核心张力，但玩家可能选择辩论、逃跑、伪造证据、拉拢证人、刺杀审判者、主动认罪换取后续机会。无论方式如何，核心张力不能消失。

### 2. 为每个大事件设计分支

每个大事件应该都有不同的分支，不同的事件结局。至少考虑：

- 玩家按原文方向行动。
- 玩家提前识破或绕开事件。
- 玩家失败或付出惨重代价。
- 玩家帮助了原本的敌人。
- 玩家误伤盟友或破坏关键证据。
- 玩家拖延导致世界默认轨迹推进。

分支不要求无限展开，但必须让主持人知道NPC和世界会如何响应。

分支不能只写成剧情散文——每个分岔都要按 SKILL.md"检定与分支触发器"落成触发器：写明触发时机、判定方式、成功/失败走向，登记进 `世界状态和世界规则/检定与触发器索引.md`，并落位到场景台本、世界共识或剧情与目标文件。原文没有骰点体系，改写时要为关键分岔补设属性/技能检定与 DC（写入 `掷骰规则.md`）；感知、理智、社交类的自动检定（进入场景即检、目击即检、无需玩家宣言）也在此时补设，并写明触发时机。

### 3. 设计失败后的继续游戏

玩家是可以失败的，但是失败不是结束。失败应当改变状态、关系、资源、世界认知或最终结局条件。

失败后的处理方式包括：

- 进入坏分支，但保留回归主线的机会。
- 失去某个盟友或资源，换取新的线索。
- 被敌人利用，进入更危险但更接近真相的位置。
- 让NPC主动行动，把玩家卷入下一次巧妙遭遇。
- 多次错误后才进入不可挽回的失败结局。

玩家偶尔导致的坏结局至少要给上几次挽回的机会，只有在错误的方向一意孤行才会失败。

### 4. 扩写文字版CG动画

原本的某些特别有张力的关键剧情部分可以用华丽的词藻，扩写成文字版“CG动画“，方便主持人引用。

CG动画适合用于：

- 开场进入世界。
- 重大真相揭露。
- 关键NPC登场或死亡。
- 仪式、审判、灾难、战争、突破、背叛等高张力场面。
- 卷末结局或最终结局。

CG动画不能替代玩家选择。它应当作为结果呈现、氛围强化或主持人素材，而不是强行规定玩家必须走到某个画面。

## 场景与角色设计

### 场景

考虑每个剧情可能发生的场景、场景的不同阶段、场景在不同时间的表现、场景的描写和内容或者可探索物品。

每个关键场景至少设计：

- 初次到达时的外观和氛围。
- 事件推进后的变化。
- 白天、夜晚或特殊时间的不同表现。
- 可探索物品、隐藏线索、危险区域。
- 在玩家成功、失败、拖延、破坏后的状态变化。

### 角色

考虑各个角色的阶段和关键数据，例如好感度的加减。考虑角色间的关系网等。

每个重要角色至少设计：

- 原文中的人物功能。
- 跑团中的诉求、恐惧、秘密。
- 对玩家的初始态度和好感度。
- 哪些行为会提高或降低好感度。
- 与其他角色的关系网。
- 在不同章节或卷中的阶段变化。
- 玩家乱玩时，该角色会如何反应。

角色不应只是剧情按钮，而应拥有自己的欲望、误判、底线和行动计划。

## 结局设计

安排几个不同的结局。包括总体主线的结局分支和各个卷甚至章节的结局分支。

结局设计应当分层：

- 章节结局：影响局部NPC、场景和资源。
- 卷结局：影响势力格局、玩家身份、世界共识和后续难度。
- 主线结局：由前面卷的完成情况总体影响最终结果。

每个结局都应当说明触发条件、达成方式、代价、后续影响。不要只有“好结局/坏结局”，应当允许混合结局，例如真相揭开但关系破裂、敌人失败但世界污染加深、主角胜利但失去人性。

## 最终交付物

完成从故事文本构建世界时，应当产出并整理：

- `模组.md`：总目录、开场白、思维导引、文件索引、特殊机制与数据面板、每个文件用途说明。**任何开局都必须产出，不能丢。**
- `故事.txt`：既定主角设定与故事前提。**它的存在标记本世界为固定开局**（运行时据此跳过车卡）。
- `开场剧情.txt`：故事开头约1000字，供主持人开局朗读。
- `开场白.md` 与 `样例开场.md`：两份精雕开场文本（见 SKILL.md"开场双文本"）。
- `世界状态和世界规则/检定与触发器索引.md`：补设的检定与全部分支触发器的对账清单，逐条标注写入位置。
- `故事集/xxx.md`：细分后的原文与扩写章节。
- 各个模组分片文件：主线、支线、NPC、场景、物品、规则、结局分支等。
- 主角 Player 文件夹：预填基础信息/格式化记忆等（固定开局玩家不车卡）。

`模组.md` 必须包含：

- 开场白：介绍情况以及要求以第一段原文故事开头。
- 思维导引：提醒主持人如何理解核心爽点、如何处理玩家乱玩、如何使用分支和失败回收。
- 文件目录：列出各个模组分片的文件相对路径。
- 故事集目录：列出各个剧情故事集文件的相对路径。
- 用途说明：说明每个文件的大致内容和使用时机。

## 完成标准

完成后检查以下内容：

- 是否保留了开头约1000字到 `开场剧情.txt`。
- 是否纯手动拆分故事，而不是用代码脚本机械切割。
- 是否没有修改和删除原文内容。
- 是否严禁脱离原文风格。
- 是否把小说核心乐趣提炼成可重复触发的方法论。
- 是否将所有章的小说情节改成可主持、可选择、可失败、可回收的跑团剧本。
- 是否给大事件、章节、卷和主线设计了分支结局。
- 分支与结局条件是否都落成了触发器并登记进 `检定与触发器索引.md`，而不是只写在剧情散文里。
- 是否为关键分岔补设了属性/技能检定与 DC，并为感知/理智/社交类场景补设了写明触发时机的自动检定。
- 是否产出精雕的 `开场白.md` 与 `样例开场.md`（原文为主体、不改写原文）。
- 是否考虑玩家意外行为与NPC反应。
- 是否整理 `模组.md` 并列出所有相关文件路径和用途。
- **是否已运行 `validate_game_structure.js` 验证目录结构，并修复所有报错直至验证通过。**
- **验证通过后，是否已按 SKILL.md"最终询问"阅读 `reference/FinalInquiry.md` 并逐条静默自查（此前禁止阅读该文件；条目可有理由地拒绝，不可敷衍跳过；不在对话中逐题作答）。**
