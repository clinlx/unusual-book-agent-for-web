# 世界数据交付约定

构建或修改角色、物品和场景文件前阅读本文件。构建流程入口见 [SKILL.md](../SKILL.md)。

## §D1 目录与引用

- 世界根目录至少提供一个可选角色槽位：`Player-<ID>`、`AIPC-<ID>` 或 `DISABLE-<ID>`。可提供多个 Player；单角色默认 `Player-pc`。ID 非空且稳定，同一 ID 不得同时出现在这三种目录中。
- 预设角色卡分别写入独立 Player 目录；游玩应用负责选择、占用和模式转换。AIPC 由 AI 扮演，结构与 KPC 一致；KPC 不可供真人选择。DISABLE 保存完整档案与物品归属，可恢复使用，但不参与当前剧情、行动或存活统计；禁用不改变 Alive/Enabled。
- 修改现有世界时保留角色 ID，明确路径和位置所属引用必须同步维护；不把禁用角色的物品释放到场景。每位玩家的已知资料独立保存，其他角色的秘密不得写入其公开字段；未公开内容使用隐藏键或主持人台本。
- 所有 JSON 使用 UTF-8，允许 BOM；必须是合法 JSON，不使用注释、尾随逗号、`NaN` 或空文件。空对象写 `{}`，空列表写 `[]`。
- 背包、NPC 列表、场景物品列表使用字符串数组，只保存索引 ID 或世界根目录相对路径。NPC、物品的详细资料保存在对应索引目录。
- 物品引用支持 `key`、`存档-索引-物品/key`、`存档-索引-物品/key/物品基础信息.json`。穿戴字典的值也使用物品引用。写作时优先采用前两种形式。
- 引用 ID 只用于关联数据；对应 `物品基础信息.json` 的 `名称` 写真实可读的服装、武器或饰品名称，`信息` 写具体外观与特征，不用 ID 代替名称或描述。人物穿戴面板会解析引用显示名称。
- 世界内引用以世界根目录为基准，不以当前文件所在目录为基准；不使用机器绝对路径或 `../`。原文和相关资料需要收进世界目录后再引用。
- 字段名属于数据接口，不作为文风措辞改写。新建资料采用约定的标准键，维护资料保留已有合法键；兼容别名不表示需要迁移键名，不另存同义字段副本。
- 物品的 `位置所属` 保存持有者或所属场景的 ID/相对路径，不能改成 `详细放置位置`，也不能用空间描述替代归属引用。口袋、抽屉等细节按公开范围写进已有描述；不强制新建额外位置字段。已有合法自定义字段保留，但不把它当作 `位置所属` 的别名。
- 玩家物品面板自动隐藏 `位置所属` 与已有的 `详细放置位置`，同时隐藏兼容键 `Location`、`Owner`、`DetailLocation`、`detail_location`；这些数据保留供主持人读取和校验，不需要为了隐藏而改名。玩家已知且需展示的外观、文字和描述放在公开信息中。

## §D2 车卡模板

车卡留白只针对待填写内容，不省略目录、文件或必填字段。以下是 `Player-pc/基础信息.json` 的可解析模板：

```json
{
  "姓名": "",
  "性别": "",
  "外貌": "",
  "穿戴": {},
  "性格": "",
  "职业": "",
  "身份": "",
  "说话习惯": "",
  "原则": "",
  "喜好/厌恶": {},
  "技能": {},
  "属性": {},
  "主动技能": [],
  "状态": {
    "HP": 1, "MAXHP": 1,
    "MP": 0, "MAXMP": 0,
    "Enabled": true, "Alive": true
  },
  "buff栏": [],
  "当前位置": ""
}
```

这里的 HP/MP 是准备阶段的占位值，不是角色最终数值。把按世界规则完成建卡、写入最终数值的步骤列入 `开场说明.md` 的“主持人开场白”部分，准备完成前不进入需要角色数值的正式检定。姓名待填时使用空字符串，不填“待定”或“【姓名】”等可能被误认为已建卡的名字。

同时创建 `背包.json`（无物品时 `[]`）、`关系记忆.json`、`格式化记忆.json`、`关系图.json`和 `待办与目标.json`。其余 JSON 按用途保留合法对象或列表。固定开局填好角色档案，其他目录约定相同。

## §D3 数值的唯一归属

- HP/MAXHP、MP/MAXMP、Enabled、Alive 只写入 `状态`。采用理智规则时，SAN/MAXSAN 也只写入 `状态`，不要求其他体系添加理智字段。
- `属性` 存基础属性；可选的 `衍生属性` 存伤害加值、体格、移动等指标。没有衍生指标时可省略这个分组。
- 同一项当前数值只保存一份，不在分组之间复制，不以大小写、中英文别名另存副本。回合历史中的数值、Buff 修正、技能消耗不属于当前值副本。
- 维护旧角色时，先核对当前文件、成功工具回执与回合结算确定有效值，再合并重复字段；冲突未查明时保留现场并报告，不猜测重置。保留独有字段不等于保留同一数值的重复副本。

## §D4 构建自查与交付说明

构建自查直接落实到世界文件并完成验证，不要求额外编写构建日志。需要向用户说明的取舍在交付说明中简述，不写入运行时游戏文件。世界目录内的文件会交给主持人读取，文件名不会自动形成读取隔离。

## §D5 验证边界

使用随附的 Node.js 验证器检查单玩家目录、JSON 语法、必填结构、索引引用、物品位置和角色数值归属。自定义字段可以保留；脚本不会判断剧情是否合理、检定是否完整落位或文风是否达标，仍需按构建流程完成内容自查。

## §D6 玩家可见资料与内部工作

人物与物品的普通字段可能直接显示在游戏面板，包括自创的“说明”“信息”“备注”和嵌套内容。任何普通字段都按将被玩家阅读来写；不要假定世界文件只给主持人看。

- **公开事实**：身份、物品外观、已经知道的用途、纸面实际文字等放普通字段。例如地址纸条只写其实际地址与外观，不附“文字资料 1 交付物”“凭它找到主线”“供主持人推进剧情”等用途分析。合法单位与公开规则说明可保留，如“1 张”“消耗 1 MP”。
- **运行资料**：秘密、触发条件、尚未揭示的物品用途、NPC 的获知来源与披露意愿，放 `.` 开头的隐藏键或场景台本。公开事实与秘密分开写，不能只把秘密夹在公开字段的括号或后半句。
- **构建工作**：写作计划、草稿批注、自查结论、修改理由按 §D4 留在世界外，不另建人物或物品的“说明”条目保存。车卡和开局选项放主持人开场白；已完成角色只保留当前身份，不写“玩家选择默认角色”“数值按某规则随机生成”等操作历史。

落盘前按玩家可见投影逐层检查：暂时遮住隐藏键和内部台本，只读剩下的键值。玩家能从中看到什么，就按正文的公开边界核对什么。纯括号过滤不能做保密：看内容用途，不看标点。结构验证通过后仍需做这一遍内容审查。

## §D7 精简状态，不维护流水日志

不再创建、追加或例行读取角色、物品、场景、世界的 `日志.txt` 类流水文件；旧存档中的这些文件不作为必读项，旧模组要求写日志的约定不再执行。当前状态直接更新对应信息、背包、世界共识与剧情进度；只有会影响后续行为的记忆和关系才精简更新，覆盖已失效内容，不逐回合抄录事件。故事经过由系统回合历史与摘要承载，不另建同用途的记录文件。

升级旧世界时，先核对旧日志中的独有事实：仍有用的设定精简并入对应基础信息、场景或记忆，保留其隐藏属性；未来默认轨迹留在台本中，不能当作已发生事实。删除重复流水和旧日志文件，同时移除模组内创建、追加、预读日志的要求。不要批量删除用户存档中的历史资料。
