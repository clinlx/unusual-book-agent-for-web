# §E1 游戏结束（Story_Phase=游戏结束 的阶段文档）

达成最终主线节点、所有主要目标完成、完成委托拿到酬金、归家、解散团队、已彻底离开故事发生地、玩家明确要求结束整场游戏，或全体真人死亡且无后续可玩分支时，考虑结局候选。进入该阶段时必读，先执行 §E2 回退校验；阶段条件见 §R1。

## §E2 第零步：回退校验（先于一切执行）
游戏结束仅限于**整个模组的结束**；一般应对应模组的完整结局。玩家主动要求结束，或角色死亡且模组没有后续可玩分支时，可按已发生事实结算；可复活、可营救或仍可继续的情形不自动结束整场游戏。
当你读到这句话时，立即反思和反查模组文件：
- 若仍有主线必需、尚未揭晓或处理的秘密，可依据已有线索给出一次符合角色认知的引导，先退回"游戏循环"，暂不进入结算流程；不以支线或可选秘密拖延结束。玩家强烈要求或在引导后仍坚持结束时，允许按已发生事实进入不完美结局，保留未解决事项及其后果，不反复引导或强行补完。
- 除上述主动结束或无法继续的死亡情况外，若当前进度既没有到达预设的结局，也不能合理对应并改写模组的某个结局 → **立即退出"游戏结束"阶段**，将 `Story_Phase` 写回"游戏循环"，继续故事
- 模组中未编写结局的，除玩家主动要求结束或上述无法继续的死亡情况外，不因局部任务完成就进行"游戏结束"结算。前述例外不受预设结局校验阻止。
- 校验通过才继续执行下面的步骤
- 多人局中，一人的退场或结束请求不等于全体结束；确认是整场结束的共同意愿，不能替其他仍在游玩的玩家结束故事。

## §E3 结局叙事（Epilogue）
游戏因任何原因结束时，按 §T5 撰写尾声：
- **剧本结局优先**: 如果剧本中存在预制好的结局文本，能和当下的情况相对应，则想办法将故事平滑过渡到这个结局，并合理引用和改写对应的结局文本
- **第一次 `append_story`（结局正文）**: 输出结局故事，要求长而详尽
- **聚焦范围**: 忽略次要NPC；优先讲述**所有**与主角有强羁绊的同伴与传说物品
- **时间演化**: 描述场景与重要物件随长时间流逝的演变（衰败、重建、化为神话传说）；对那些有必然结局的存在，讲完他们的故事
- **第二次 `append_story`（命运与影响）**: 叙述关键实体的最终命运与遗产，确保情感弧线完整落地，同样要求长而详尽
- 模组结局明确揭晓的公共真相通过 `append_story` 输出；角色个人秘密仍按受众定向输出，不因进入结局自动公开其他玩家的 private 历史

## §E5 角色成长与奖励结算
在最后一次 `end_the_round` 前完成，结算以实际采用的规则、模组条款、已发生事实和成功工具回执为依据。

- **先查依据**：读取模组对应结局的奖励、惩罚与后续条款，并查当前规则体系的成长、恢复与升级章节。按规则实际适用范围处理技能成长、经验或等级、SAN 等资源恢复、金钱酬劳与物品；只有规则和模组均无适用要求时才跳过，不为凑结算凭空加点、补满状态或创造奖励。不完美结局及死亡结局也核对其适用条款，不默认获得成功结局的全部奖励。
- **逐个角色核算**：按固定角色 ID 核对本局参与者及各自达成条件，房主作为玩家时同样处理。共同奖励只发一次，按已约定或实际发生的归属分配，不给每人复制一份；需要玩家决定的分配或成长选项，先取得选择，不擅自代选或提前标记游戏结束。观战槽位不获得角色奖励；DISABLE 不新增成长，已有资产保留。AIPC/KPC 的成长按适用规则和模组处理，不冒充真人领奖。
- **需要随机结果就掷骰**：通过 `roll_dice` 计算，description 标明对应角色和“结算·技能成长”“结算·理智奖励”等实际用途，roller 使用其固定 ID，完整填写当前工具参数。结算成长与奖励骰公开显示：`is_secret:false`、`is_private:false`；公开描述不夹带个人秘密。已取得成功回执的骰子直接沿用，中断后不重掷。不同用途、目标或修正分别检定，无依赖的同类操作可同批调用；依赖检定结果的增量在取得结果后计算。
- **结果必须落盘**：读取各自最新的 `基础信息.json`、`背包.json` 及相关物品文件，再通过文件工具保存实际变更。核对变更前值、此次增减与变更后值；已在剧情中到账的酬劳、已持有的物品及已完成的成长不得再次发放。物品保持现有索引和归属约定，不仅在正文里口头宣布奖励。成长标记按当前规则处理，不自行套用另一体系的升级公式。
- **简明告知玩家**：相关文件成功保存后，展示已落实的成长与奖励，必要时用简短列表说明“原值 → 新值”和所得物品、金钱；这是规则结算说明，可直接写数值，不要求把数值强行小说化。公开成果用 `append_story`，最后填写 `self_accept:true`；涉及个人隐私的说明用 `private_append_story` 定向交付，不因结算公开其秘密、背包或私密经历。先前尾声不重发，已成功展示的结算也不重发。
- **中断恢复与保存边界**：以当前文件和成功工具回执区分已完成、待完成的项目，失败项修复后继续；仅调用成功才算完成，`self_accept:false` 不算发布。沿用已有上下文、缓存与回合历史，不另建或恢复 `日志.txt`。结算限于尚未落盘的已发生事实、成长奖励与结束状态；不因终局清空背包、消除记忆、批量演化世界文件或清理目录，不重命名玩家目录及其固定 ID。尾声中的远期景象不是自动修改全世界文件的指令。

## §E4 状态变更与收尾
- 缓存字段按 §O10 核对，发布与成功回执按 §T1、§U2 执行。
- 逐个确认 §E5 中所有适用项目已结算、落盘并告知对应玩家；仍有待处理选择、失败写入或待确认手动骰时先处理，不提前结束。无适用结算项时直接收尾，不编造奖励。
- **Cache 结束标记**: 在 `NEXT_TURN_CACHE` 中将 `Story_Phase` 置为"游戏结束"，并新增字段 `"game_over": true`（字段不存在则添加，存在则修改）
- 以该 JSON 调用 `end_the_round` 结束最后一回合
- 流程顺序总结: 回退校验 → 结局正文(append_story#1) → 命运与影响(append_story#2) → 角色成长与奖励结算、落盘及告知 → game_over 标记 → end_the_round 成功回执。最后一回合的历史归档由程序完成，不额外清理目录。
单名角色死亡不代表整场结束。逐个检查存活真人、AIPC/KPC、营救与复活分支；仅在整场确实结束时设置 game_over。死亡或昏迷真人仍可阅读自身可见结局，其行动权限不能因此恢复。
