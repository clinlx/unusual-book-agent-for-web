# §E1 游戏结束（Story_Phase=游戏结束 的阶段文档）

结局候选在达成最终主线节点、全体真人死亡且无后续可玩分支、或所有主要目标完成时出现，进入该阶段时必读，先执行 §E2 回退校验；阶段条件见 §R1。

## §E2 第零步：回退校验（先于一切执行）
游戏结束仅限于**整个模组的结束**；一般应对应模组的完整结局。玩家主动要求结束，或角色死亡且模组没有后续可玩分支时，可按已发生事实结算；可复活、可营救或仍可继续的情形不自动结束整场游戏。
当你读到这句话时，立即反思和反查模组文件：
- 除上述主动结束或无法继续的死亡情况外，若当前进度既没有到达预设的结局，也不能合理对应并改写模组的某个结局 → **立即退出"游戏结束"阶段**，将 `Story_Phase` 写回"游戏循环"，继续故事
- 模组中未编写结局的，除玩家主动要求结束或上述无法继续的死亡情况外，不因局部任务完成就进行"游戏结束"结算。前述例外不受预设结局校验阻止。
- 校验通过才继续执行下面的步骤

## §E3 结局叙事（Epilogue）
游戏因任何原因结束时，按 §T5 撰写尾声：
- **剧本结局优先**: 如果剧本中存在预制好的结局文本，能和当下的情况相对应，则想办法将故事平滑过渡到这个结局，并合理引用和改写对应的结局文本
- **第一次 `append_story`（结局正文）**: 输出结局故事，要求长而详尽
- **聚焦范围**: 忽略次要NPC；优先讲述**所有**与主角有强羁绊的同伴与传说物品
- **时间演化**: 描述场景与重要物件随长时间流逝的演变（衰败、重建、化为神话传说）；对那些有必然结局的存在，讲完他们的故事
- **第二次 `append_story`（命运与影响）**: 叙述关键实体的最终命运与遗产，确保情感弧线完整落地，同样要求长而详尽
- 模组结局明确揭晓的公共真相通过 `append_story` 输出；角色个人秘密仍按受众定向输出，不因进入结局自动公开其他玩家的 private 历史

## §E4 状态变更与收尾
- 缓存字段按 §O10 核对，发布与成功回执按 §T1、§U2 执行。
- **Cache 结束标记**: 在 `NEXT_TURN_CACHE` 中将 `Story_Phase` 置为"游戏结束"，并新增字段 `"game_over": true`（字段不存在则添加，存在则修改）
- 以该 JSON 调用 `end_the_round` 结束最后一回合
- 流程顺序总结: 回退校验 → 结局正文(append_story#1) → 命运与影响(append_story#2) → 数据结算 → 目录清理与历史锚定 → game_over 标记 → end_the_round
单名角色死亡不代表整场结束。逐个检查存活真人、AIPC/KPC、营救与复活分支；仅在整场确实结束时设置 game_over。死亡或昏迷真人仍可阅读自身可见结局，其行动权限不能因此恢复。
