# 大纲拷问与共识护栏

**适用层级**：拷问流程服务全书/全卷大纲级任务的 L0-L4（必要时延伸到 L5 的开头十章决策）；共识护栏覆盖所有层级的修改类任务。
**解决问题**：大纲级请求的拷问式访谈、样例化选择、爽点与 XP 探知、隐性前提挖掘、破坏性修改护栏。
**不解决**：不替代日常任务的轻量协作（一次一问、合理假设的默认方式在 collaboration-and-questioning.md），不负责章节工程与正文执行。
**缺前置时**：不确定当前层级时回看 granularity-orchestration.md；非大纲级任务回看 collaboration-and-questioning.md。

拷问的骨架是把粒度阶梯当作访谈的设计树：沿阶梯逐层下行、按依赖顺序解决决策、一次一问、每问附推荐答案、共识达成前不动工；在此之上补创作域特有的三件事：样例化选择、爽点探知、隐性前提挖掘。

条目：§Q1 两种协作强度 ｜ §Q2 拷问式访谈流程 ｜ §Q3 主动升级点子 ｜ §Q4 样例化选择 ｜ §Q5 爽点与 XP 探知（含爽点档案）｜ §Q6 隐性前提挖掘（含反差找基线）｜ §Q7 共识护栏（含商讨协议）

## §Q1 两种协作强度

本 Skill 默认轻量协作：信息足够就直接产出，缺口用合理假设补，能少问就少问。全书大纲级任务是例外——决策密度高、返工代价大、用户的爽点常常藏在脑内没说出来，此时轻量协作会把模糊点子直接铸成模糊大纲。

进入拷问模式的条件（满足任一）：

- 用户要求设计或重构全书/全卷级大纲、主线或结局回收。
- 用户抛出点子希望展开成完整作品，且点子里有多处不明确、互相冲突或只有模糊感觉的部分。
- 用户明确要求深入打磨、反复讨论、“帮我问清楚”。

不满足就不要拷问。写一章、改一段、设计一个配角走轻量协作，过度追问会打断创作。

## 拷问式访谈

### §Q2 流程

1. **点子勘察**：通读用户给的全部材料（点子、设定、片段、聊天记录、原型作品），分成两堆——**已定事实**自己读取和推导，不要拿去问；**待决决策**列成清单，标出不明确、互相冲突、只有模糊感觉的部分。
2. **逐层拷问**：按 L1 核心乐趣 → L2 主线承诺 → L3 结构骨架 → L4 系统支架下行。层内按分支逐个解决，例如 L4 分人物、伏笔、世界观三支。上层答案会改变下层要问什么，所以不要并行轰炸。
3. **一次一问**：等用户回答后再问下一个。每问必附推荐答案和一句话理由（服务哪个爽点、哪层结构），让用户可以只回“就按你说的”。品味类决策用样例化选择。
4. **分层小结**：每层走完，输出本层已定决策清单，用户确认后再下钻。
5. **共识闸门**：全部层级确认后才产出完整大纲。产出必须与已确认决策一致，不要临时加戏；写作中发现已确认决策有问题，回来重新商讨，不要私自偏离。

### §Q3 主动升级点子

拷问不是被动记录用户答案。每一层都要尝试给出比用户原始点子更强的开创性方案：更狠的反转、更痛的代价、更缠的关系张力、更省的结构。规则：

- 改进必须用样例呈现，放在用户原案旁边，让差异可感。
- 供用户选择或拒绝，不强行替换；用户拒绝的方向记入爽点档案，负样本同样有信息量。
- 升级要服务已探知的爽点，不要炫技式加戏。

### §Q4 样例化选择

品味类决策不要用抽象问题问。用户说不出“我想要什么样的关系张力”，但对具体样例的反应是可靠的。

- 每个选项写成 100-300 字的具体样例：场景片段、对话或桥段梗概，能体现差异核心即可。
- 样例之间只变一个轴：关系位置、权力方向、情绪类型、节奏密度。一次变多个轴，用户的选择无法归因。
- 给 2-3 个样例，附自己的推荐和理由。
- 用户的每次选择与拒绝都登记进爽点档案。

## §Q5 爽点与 XP 探知

XP 在网文语境指读者的深层偏好按钮：偏爱的关系张力、情绪类型、人设、桥段，不限于情色。用户往往说不清自己的 XP，但它决定这本书真正写给谁看。探知要主动、直接、无评判，不要让用户觉得需要为自己的偏好辩解。

### 探知手段

- **听高能词**：用户描述点子时在哪些地方反复、加细节、语气升温，那附近就有 XP。
- **原型反推**：问“想复现哪部作品哪个场景的感觉”，再用 §M3 meme 剖析法拆出感受层和关系层，那就是 XP 的成分。
- **样例试探**：给只差一个轴的样例对（同一场景的支配/依赖版与敌对/理解版），从选择模式反推偏好。
- **命名确认**：探测到疑似 XP 后，用平实语言直接说出来向用户确认——“你要的核心是不是‘强者只在唯一弱点前失控’？”确认过的才能作为设计依据。

### 爽点档案

拷问过程中持续登记，作为后续所有层级设计的输入：

```text
爽点/XP：
- 命名：
- 来源（高能词 / 原型场景 / 样例选择 / 被拒绝的方向）：
- 关系内核（谁对谁、什么张力）：
- 情绪类型：
- 触发前提（读者必须预先知道什么才会爽）：
- 确认状态：疑似 / 已确认 / 已否认
- 挂载位置（主爆点 / 副爆点 / 关系线 / 日常）：
```

## §Q6 隐性前提挖掘

用户脑内常有只有自己知道的意境：人物的过往、力量的稀有度、身份的分量、某件事的禁忌程度。这些前提是点子让用户快乐的基础，但用户不知道需要表达、也不知道如何表达。不挖出来，写出的正文只对用户一个人成立——这是“作者觉得爽、读者莫名其妙”的最大来源。

本条挖的是**信息侧**缺口：读者需要预先知道什么，这一幕才成立。前提是用户自己知道要什么，只是没说清背景。若连这一点都不成立——用户拿出一个自认为很好但读起来平淡的片段，说不清想要的到底是哪种爽——那缺的是欲望本身而非背景信息，先用 `desire-analysis` 技能的剥离测试倒推出核心诉求，再回本条把它转成铺垫义务。

### 挖掘手段

- **零上下文复述检验**：把用户的点子按零背景读者的视角复述一遍。复述后爽感消失的地方，就埋着未表达的前提。
- **追问快乐来源**：对用户觉得“很爽/很有画面感”的点子问具体：这个画面为什么让你兴奋？读者需要预先知道什么，这一幕才成立？在场的是谁、他们此前怎么看主角？
- **反差找基线**：多数爽感是反差爽。问清“原本应该是什么样”——羞辱的前提是地位，打脸的前提是轻视，失控的前提是一贯克制。基线没立进正文，反差就不存在。

### 常见隐性前提类型

| 类型 | 未表达时的症状 |
|---|---|
| 关系历史 | 重逢、背叛、守护显得突兀廉价 |
| 稀有度/难度 | 成就无分量，读者不知道这有多难得 |
| 禁忌程度 | 越界没有张力，读者不知道这不被允许 |
| 身份的社会含义 | 跌落或加冕无感，读者不知道这个身份意味着什么 |
| 反差基线 | 打脸、失控、崩坏无从对比 |
| 原型既有印象 | 用户默认读者看过某原型作品，实际读者没有那份预装情感 |

### 转化为铺垫义务

挖出的前提必须转化为正文义务，否则挖掘无意义：

- 写入爽点档案的“触发前提”栏。
- 在 L3 结构层分配铺垫位置：哪一卷哪个阶段把这个前提立起来——这正是第一共鸣三检验（§M8）中“理解”的来源。
- 属于信息的进伏笔账本（§T4），属于欲望的进情绪线账本（§T5）。

## §Q7 共识护栏

修改类任务（改稿、调设定、重写段落、局部换剧情）遇到以下任一情况，先商讨再动手：

- **破坏性修改**：改动会摧毁已埋伏笔、已建立的情绪线、爽点结构或主爆点的延迟兑现。
- **上下文不足的单点修改**：不了解前后剧情、当前情绪状态和连锁剧情就改这一处，效果必然下降。先读相关章节和账本，读不到就问。
- **显著事实冲突**：改动与已确立的设定、时间线、人物既有行为矛盾，或用户的新要求与旧共识矛盾。

### 商讨协议

护栏不是拒绝，而是“勘察影响 → 摆出方案 → 等待确认”：

1. 先自己勘察：读相关章节、伏笔账本、情绪线账本，把连锁影响找全。能查到的事实不要拿去问用户。
2. 用具体清单指出影响链：波及哪些伏笔、哪条情绪线、哪个未兑现的爆点、哪些既有事实。
3. 给 2-3 个方案：最小代价版（保留原结构的局部改法）、折中版、原案照做版（写明代价）。
4. 用户确认后执行。用户坚持原案就照做，把已知代价写明即可，不要阳奉阴违。

护栏同样约束自己：发现自己将写的内容与既有事实或情绪线冲突时，停下来先对齐，不要私自“顺手修正”用户的设定。
