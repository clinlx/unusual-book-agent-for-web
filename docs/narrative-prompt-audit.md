# 文风、成品边界与提示词执行链审计

审计日期：2026-10-07。当前项目基线：`25d6ff1`。对照目录：`C:/Users/Administrator/source/repos/AgentWithToolApplication`，阅读的是当前磁盘中的 `sys_prompt_ori.md`、`next_round.md` 和 `WorldTemp/Prompt/Temp/回合提示词.md`，不把它们冒充截图生成当时的历史版本。证据来自源码、用户截图及公开研究；没有取得两次生成的完整请求，未对用户的实际模型做重复 A/B 试验。

## 判断

差异不只在模型训练习惯。项目中存在可以直接定位的反向示范、粗粒度审校、样例复用和公开字段定义缺口。它们足以解释为什么“写得自然”“加编号”之后仍可能出现同样的问题。源码证明这些诱因存在，不能单凭源码确定它们各自对某次生成贡献了多少。

“更多逻辑规则会把模型切换到专家模式，从而覆盖训练文风”不是已经验证的机制。规则可以改变当前任务的条件与输出倾向；模型权重没有因此被改写。编号也只是便于定位的文本，不是强制跳转、函数调用或保证被执行的程序。

## 1. 更深层的差异

| 层面 | 具体证据 | 对结果的影响与判断 |
|---|---|---|
| 指令强度 | 参考项目 `sys_prompt_ori.md` 的 T7 单列“命中即改写”的句式黑名单；本项目此前只有直述优先、修辞低频、句法连贯 | “偶尔可以”留下很大的解释空间。T7 确实漏移植，但它主要针对转折定义、否定排比，并不能证明参考项目完整禁止了所有短句或用户列举的所有套语 |
| 指令与示例冲突 | 设计器 `OpeningCraft.md`、`write-novel/references/prose-and-formatting.md` 把“转身离开。没回头。心跳很快。”当作好例子 | 文字说要自然，示例却直接演示碎句。模型可能学到示例的句法，而不是抽象要求的意图 |
| 情绪展开被压缩 | 两份设计器文档要求“至多一句即时身体反应或短念头”“判断要短、要快” | 容易把消除重复误解为删除情绪形成过程，留下心跳、呼吸、目光等易复用的短片段 |
| 背景的放置 | 设计器要求背景排在最后、读者靠动作推断关系 | 为避免解说而让角色已知背景也消失。读者看到反应，却不知道是谁、为什么在意；有限视角不要求隐去角色本来知道的事实 |
| 感官的组织 | `DesireAndTextureCraft.md` 要求视觉、听觉、嗅觉、触觉逐项给实感 | 容易形成五感清单。游戏端已说不设感官配额，设计端仍保留逐项铺陈，两个生成阶段相互抵消 |
| 样例的反馈 | 世界构建技能要求样例兼作全程范本；游戏 `system/round.md` 会读取并学习它 | 设计器生成的坏样例进入游戏，又与后续同风格正文一起成为持续示范。这是上下文内重复强化，不是模型在游戏中重新训练 |
| 审校粒度 | 本项目回合审校主要列“文风、保密、收尾”；参考项目 phase 4f 重复具体禁句，phase 4g 明确样例服从系统文风 | 泛化自评很容易放过具体毛病。具体对象、检查动作、修改去向比“认真审校”更有可执行性 |
| 迭代真实性 | 两边所读回合文件都以伪代码要求模型编排、起草、自查 | 文字中的两个步骤不能证明程序执行了两次模型调用。不能把参考项目效果归因于未经证实的独立多轮审稿 |
| 跨回合纠偏 | 参考项目 `回合细则.md` 的细则 6、7 把发布后发现的问题存进 Cache 或 `per_round_note.md`，下一轮 phase 4 使用 | 这是另一处实质差异：把发现的问题变成下一轮的输入，而非每轮重新泛化自检。本项目此次使用可选缓存字段衔接，避免另增一份世界内说明文件 |
| 发布时机 | `append_story` 成功后正文已发布；`after_story` 做落盘补漏 | 此时再发现文风错误已经太晚。修订必须在发布之前；“发布后再检查”的步骤不能修好刚才的正文 |
| 公开字段 | `src/game-data.js` 的 `visible()` 递归过滤隐藏键等固定项；普通“说明”“信息”会保留 | 字段里的设计注释会照样显示。括号不构成隐藏标记，增加一个叫“说明”的字段也不构成内部工作区 |
| 写作格式 | 设计器小说技能的标点表把 `［］` 定义为“补充说明、编辑标记”，没注明只供工作文档 | 容易让内部批注获得形式上的许可。应按产物用途隔离，而不是全面禁止正常括号 |
| NPC 的可说性 | 主持人规则检查 NPC 是否知道，缺少同等明确的披露意愿、当下动机与披露范围 | “知道”会被偷换成“应当告诉玩家”。雇主因模型知道地图而列出全套路线，不是单纯泄露未知事实，更是对话动机失真 |
| 主次权重 | 参考项目 R4 与每轮提示反复强调叙述为主体、状态机为辅助；本项目有连贯成稿要求，但流程占据大量注意位置 | 比起再增加“白金作家”的称号，保持成稿点的实际文学示例、压清流程与正文的边界更值得试验；不能据此断言规则越多文笔越好 |

## 2. 截图应该怎样量化

按第二张截图人工转录从“叮铃”到“第三声铃响”的梦境片段，计数只包括汉字：

- 以 `。！？` 划分完整句：15 句，4 句不足 10 字，占 26.7%，中位数 14 字。
- 再以逗号、顿号、分号、破折号分割片段：34 段，26 段不足 10 字，占 76.5%，中位数 7 字。

第二种包含列举项，不等价于语法上的独立句。它支持“很多句子靠逗号串联短片段”的观察，不能表述为“超过七成完整句不足十字”。把句号换成逗号可让第一项变好，却不会改善叙述。

“声音被风吹散”并非严格意义上的跨感官通感，短句和隐喻本身也不是小说禁忌。这次遵从的是项目明确的语言偏好：普通旁白排除这类套语与碎短句；对白、拟声和指定照录原文另设范围。评价重点仍应包括搭配是否成立、读者能否理解处境、段落有无前后关系，不能只优化字数。

第一张截图末句离开人物所在的事务所，去断言旧宅“灯还黑着”，需要角色观察或其他可靠来源。仅使用“你”不保证有限视角，换成第三人称也不是根因。信息来源才是检查对象。

第三、四张截图体现的是交付层混写：公开物品信息混入了交付用途，公开人物说明混入建卡过程。模型生成了幕后说明、程序正常展示普通字段，这两步可以同时成立。不能靠把字段名“说明”全部隐藏来解决，否则合法的公开说明也会丢失。

## 3. 当前修改

游戏端在原有编号之后追加，未重排既有编号：

- F4：普通人物、物品字段视为发布，公开事实、运行秘密、构建批注明确分开。
- T6：具体句式黑名单、普通旁白短句下限、逗号碎片检查、主谓宾与比拟对象检查，附可直接模仿的正常表达。
- T7：内部计划与成品边界，括号、附注、独立说明段一并检查；有限视角按信息来源判断。
- T8：先审内容和披露范围，再审语言与场景；命中后修改具体句段并复核，修订意见不进入成品。
- N6：知道什么、为何愿意说、为何此刻说、说多少。未被询问时可以有合情境的主动发言，但不能自动变成调查路线菜单。
- 回合伪代码、每轮注入与开场流程接入上述条目；固定工具说明仅保留自包含的用途、参数与成品边界，不引用可被替换的提示词编号。样例有问题时不模仿其错误，明确照录的原文仍保留。
- 发布后发现而无法回改的问题，可通过内部缓存 `Narrative_Review` 留最多三条纠偏动作，下一轮明确消费，已解决项清除；不把批注写进公开资料，也不反复复制坏句。

设计器同步处理两个实际入口：常驻 `game-world-builder` 和可调用 `write-novel`。调整开场反向示例、压缩反应的要求、逐项感官要求、编辑标记适用范围；补入两遍修订和可见字段检查。`OpeningCraft` 的 O 编号、小说技能的 P 编号与游戏主持人的编号各在自己的上下文内解释，不把它们当全项目同一套编号。

设计器和游戏运行时的提示词互不可见，禁止相互引用编号或提示词路径。两端分别保有完整的规则与示例；交接只通过生成的世界文件表达事实、台本和样例。描述下游用途不能代替本端的具体执行要求。

没有加入按关键词自动删除整段小说、禁止所有括号或隐藏所有“说明”的程序。语义判断不够可靠时，这样的硬过滤会误伤；本次修改是提示词与交付约定，并非能阻止每一次违规的运行时审核器。

## 4. 方法论依据及适用边界

1. **管理上下文中的示范与竞争指令。** Anthropic 的 context engineering 文档建议保持高信号上下文并使用清楚的示例。应用到本项目：去掉与目标相反的好例子，保留少量完整的正常段落，在必经成稿点放简短检查，避免所有参考资料无差别常驻。这是工程推断，不是该文对中文小说效果的直接实验。[原文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
2. **重视位置，但不神化编号。** Lost in the Middle 在检索和问答任务中观察到信息位置影响模型利用率。它支持检查长上下文布局，但不直接证明把文学规则放尾部必然提高小说质量，更不证明某个编号能固定注意力。[论文](https://arxiv.org/abs/2307.03172)
3. **反馈要具体，修订要实际发生。** Self-Refine 将初稿、反馈、改稿组成迭代流程，在其测试任务上优于一次生成。迁移到这里，最有价值的是反馈指出具体句子及问题，随后产出修改稿。不能把论文总体收益套到当前模型，也不能把一次请求中写“审校两遍”当成复现了该实验。[论文](https://arxiv.org/abs/2303.17651)

提示词可以降低特定表达在当前上下文中的出现倾向，不能永久擦除训练习惯。更强的方案包括有代表性的正例、分离生成与审稿请求、基于真实失败样本的评测；如服务支持，再考虑高质量风格数据微调。提高温度可能同时增加不自然搭配，降低温度也可能固化高概率套话，不能代替内容与流程设计。本次未修改采样参数。

## 5. 如何验证下一步，而不是无限叠提示词

固定模型、采样参数、玩家输入和世界文件，设置至少四组对照：基线；只改设计器样例；只改运行时规则；两端一起改。每组多次采样，分别跑全新开局与连续回合；生成世界本身的波动与主持人续写的波动分开测试。

用相同的五类场景评估：梦醒后的相认；雇主委托且玩家未问路线；玩家主动询问但 NPC 无获知来源；人物与物品公开字段含内部说明的修复；长上下文续局中旧样例持续出现。评审时隐藏实验组别。

记录原始回复和以下项目，而不是只问模型“自然吗”：

- 旁白独立短句、逗号碎片、指定套语的出现次数；同时保留对白与照录原文的例外标记。
- 玩家是否知道自己是谁、在哪里、为何在意，关键变化是否有过程。
- 每条新披露信息的来源与 NPC 动机，是否无端列调查路线。
- 正文与公开字段里的作者批注、幕后用途、未来事实是否为零。
- 盲评的自然度、连贯性与沉浸感；人工判断是否为了过规则而凑字、删情节或写成长清单。

如果仍频繁失败，下一步应做程序层独立审稿：内部草稿 → 审稿请求返回问题位置 → 修订请求 → 复核 → 发布。审稿结果与草稿不进入玩家正文及公开文件；重试设上限，超限时保留未发布状态，不能无限改写或先发布再补救。它会增加延迟与调用成本，需要用以上对照验证收益，而不是默认更复杂就更好。

## 6. 验证范围与生效条件

自动化测试可以验证编号可解析、修改进入两页构建产物、公开字段与隐藏字段按既定规则显示；不能证明模型已经稳定学会自然文风。

源码显示游戏设置的 `promptOverrides` 可替换默认提示词，世界根目录的 `system.md` 会附在系统提示后，活动回合还会冻结当前提示词配置。设计器的世界构建技能为常驻注入，小说技能仍需要实际加载其正文参考；用户导入的技能也可能与内置版本不同。因此重新构建并不等于所有旧存档和正在执行的回合都已使用本轮修改。

本次没有检查或改动用户浏览器里的实际设置、存档、原始样例和已发布正文。验证实际效果时，应保存有效请求中的提示词版本、覆盖项与已读样例；旧世界若已经存着坏样例或公开批注，需要针对该世界修复，修改程序内置提示词不会追溯替换它们。
